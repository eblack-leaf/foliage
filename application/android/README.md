# android/

Generated by `foliage_android` -- do not hand-edit, regenerate instead:

```sh
cargo run -p foliage_android -- gen \
  --app-id io.github.eblackleaf.application \
  --lib-name application_android \
  --out application/android
```

Everything here is a parameterized copy of `rust-mobile/android-activity`'s own
`agdk-mainloop` example (the crate that implements winit's `android-game-activity` backend),
which is what `application_android`'s `[lib] crate-type = ["cdylib"]` + `android_main` entry
point (`application_android/src/lib.rs`) target. `androidx.games:games-activity` -- Google's
`GameActivity`, not the older plain `NativeActivity` -- has a real Java/Kotlin AAR dependency,
so a Gradle project is genuinely unavoidable here, not a workaround.

`android_main` lives in its own `application_android` crate, not in `application` itself --
a cdylib target also produces a competing `wasm32-unknown-unknown` artifact sharing
`application`'s own binary name, which broke trunk's build (`found more than one target
artifact: ["application", "application"]`). `application_android` just depends on
`application` and calls its `pub fn run`; nothing else in the workspace depends on
`application_android`, so it can't affect the wasm or desktop builds.

## One-time environment setup

This is the part that's normally the friction -- Android Studio's setup wizard, hand-picking
SDK components, clicking through license dialogs. It's all doable from a terminal instead;
`sdkmanager` accepts licenses non-interactively, no Studio required.

1. **JDK 17** -- via your OS package manager, or https://adoptium.net if it doesn't have one.

2. **Android SDK command-line tools** -- get the current "command line tools only" zip for
   your OS from https://developer.android.com/studio#command-line-tools-only (the exact
   filename/build number changes over time, so grab whatever's current there rather than a
   pinned link here). Then:

   ```sh
   mkdir -p ~/android-sdk/cmdline-tools
   unzip commandlinetools-*.zip -d ~/android-sdk/cmdline-tools
   # the zip extracts to `cmdline-tools/cmdline-tools` -- sdkmanager only finds itself
   # correctly if that inner folder is named `latest`. This trips a lot of people up.
   mv ~/android-sdk/cmdline-tools/cmdline-tools ~/android-sdk/cmdline-tools/latest

   export ANDROID_HOME="$HOME/android-sdk"
   export PATH="$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH"
   # put both exports in your shell rc file so they persist
   ```

3. **Install exactly the packages this project needs, and accept licenses, non-interactively:**

   ```sh
   yes | sdkmanager --licenses
   sdkmanager "platform-tools" "platforms;android-35" "build-tools;35.0.0" \
     "ndk;27.3.13750724"
   export ANDROID_NDK_HOME="$ANDROID_HOME/ndk/27.3.13750724"
   # this one too, in your shell rc file
   ```

   (`27.3.13750724` is the current NDK LTS release as of writing -- check
   https://developer.android.com/ndk/downloads if you want the latest instead; any
   reasonably recent NDK works, cargo-ndk doesn't care which.)

4. **Rust side:**

   ```sh
   rustup target add aarch64-linux-android   # add other ABIs only if you need them
   cargo install cargo-ndk
   ```

None of this is Gradle-project-specific -- it's a one-time machine setup, done once no matter
how many Android/Rust projects you build afterward.

## Build

```sh
cargo ndk -t arm64-v8a -o application/android/app/src/main/jniLibs/ \
  build --release -p application_android
cd application/android && ./gradlew assembleDebug
```

The APK lands at `app/build/outputs/apk/debug/app-debug.apk`.

**Getting the APK onto your phone:** transfer the file however you like (USB file copy,
email yourself, syncthing, whatever) -- no `adb`/USB-debugging link required. The one thing
that trips people up here: your phone will refuse to install it until you allow it. Whatever
app you use to open the APK file (Files, a browser download, etc.), Android will prompt
"Install unknown apps" the first time -- allow it for that one app, then tap the APK again.
(If you'd rather use `adb` after all: `./gradlew installDebug`, or `adb install
app/build/outputs/apk/debug/app-debug.apk`, does the transfer+install in one step -- entirely
optional, not needed for the manual-transfer path above.)

**Picking `-t <abi>`:** `arm64-v8a` covers essentially every phone made since ~2017. If
you're unsure of your specific device, Settings -> About phone usually shows the chipset, or
once you have a USB connection at all, `adb shell getprop ro.product.cpu.abi` reports it
directly.

## Release signing

`assembleDebug` needs nothing extra -- AGP auto-generates and uses a debug keystore for you.
`assembleRelease` also runs without one, but produces an **unsigned** APK that no device will
actually install. To get a real signed release build:

1. Generate a keystore once (the JDK's `keytool` already has everything needed -- no extra
   install). Keep the resulting file and passwords somewhere safe outside the repo; losing
   this keystore means you can never ship an update to the same `applicationId` again under
   the same identity.

   ```sh
   keytool -genkeypair -v -keystore ~/keys/application-release.keystore \
     -alias application -keyalg RSA -keysize 2048 -validity 10000
   ```

2. Create `application/android/keystore.properties` (gitignored, never commit it):

   ```properties
   storeFile=/home/you/keys/application-release.keystore
   storePassword=<the password you set above>
   keyAlias=application
   keyPassword=<same password, unless you set a separate key password>
   ```

3. That's it -- `app/build.gradle`'s `signingConfigs.release` reads this file automatically
   whenever it's present:

   ```sh
   cd application/android && ./gradlew assembleRelease
   # -> app/build/outputs/apk/release/app-release.apk, already signed
   ```

   No `keystore.properties`? `assembleRelease` still succeeds, just produces an unsigned APK
   at the same path -- fine for a build-check, not for something you actually install.

## Troubleshooting

- **Gradle sync fails with "some licenses have not been accepted"**: `ANDROID_HOME` gradle is
  using doesn't match where you ran `sdkmanager --licenses`. Check `local.properties`
  (gradle writes the SDK path it's actually using there) or just rerun `yes | sdkmanager
  --licenses` with `ANDROID_HOME` exported to the same path.
- **`cargo ndk` says it can't find the NDK**: `ANDROID_NDK_HOME` isn't set/exported, or points
  at the wrong version directory -- it should be `$ANDROID_HOME/ndk/<version>`, not
  `$ANDROID_HOME/ndk` itself.
- **App installs but crashes immediately**: check `adb logcat` if you have a USB connection
  available, even a temporary one just for debugging -- `System.loadLibrary` failing because
  `--lib-name` doesn't match the cdylib's actual output name is the most likely first-time
  cause.

## Regenerating

Everything under `android/` except this README is disposable -- delete and rerun the `gen`
command above any time (e.g. after bumping `--games-activity-version`/`--gradle-version`/SDK
levels). `app/src/main/jniLibs/` and `app/build/` are gitignored build output, not part of
what `gen` writes.
